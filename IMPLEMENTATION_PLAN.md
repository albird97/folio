# Folio implementation plan

Folio is one PDF product with three targets: a macOS app, a Windows app (both Tauri 2) and a
Chrome extension (Manifest V3). Document logic is written once in shared packages; each target
contributes only a thin platform adapter and its own shell.

- **Status:** Phase 1 (Foundation) is complete. See [Phase 1 results](#6-phase-1-results).
- **What works where:** [PLATFORM_CAPABILITIES.md](PLATFORM_CAPABILITIES.md) (generated, tested).
- **How to build and run:** [README.md](README.md).

## 2. Architecture

```
apps/
  desktop/            Tauri 2 shell: Vite + React UI, Rust commands (src-tauri/)
  chrome-extension/   MV3: popup, side panel, editor page, options, service worker
packages/
  document-model/     Types, branded IDs, operations, undo/redo history, recovery snapshots
  pdf-core/           PDF.js engine wrapper, errors, sniffing, hashing, Vite asset plugin
  platform-adapters/  Adapter contract, web/memory adapters, capability matrix
  shared-ui/          Design tokens, Tailwind v4 theme, primitives, icons, brand mark
  editor/             The shared workspace UI and its Zustand stores
tests/
  fixtures/           Real PDFs (pdf-lib + qpdf), regenerated by scripts/generate-fixtures.ts
  e2e/                Playwright: extension/ (unpacked in Chromium), desktop-web/ (UI in Chromium)
  desktop/            WebDriver test of the real desktop binary (tauri-driver)
```

Dependency direction is strictly downward:

```
apps/desktop ─┐                        ┌─ document-model (no DOM, no platform APIs)
              ├─ editor ─┬─ pdf-core ──┤
apps/chrome ──┘          ├─ platform-adapters ─ document-model
                         └─ shared-ui
```

Internal packages are consumed as TypeScript source (`exports` point at `src/`), so there is no
package build step. Vite bundles them per target.

### 2.1 Platform adapters

`PlatformAdapter` (packages/platform-adapters/src/types.ts) is the only way shared code touches
the platform:

| Concern        | Desktop (Tauri)                                              | Chrome extension                         | Web (dev/tests)       |
| -------------- | ------------------------------------------------------------ | ---------------------------------------- | --------------------- |
| Pick files     | Native dialog shown **by Rust**                              | `<input type=file>` in a page            | `<input type=file>`   |
| Incoming files | Drag and drop, launch arguments, Finder events → Rust grants | Side panel → editor hand-off (IndexedDB) | `deliverFiles()`      |
| File reads     | `read_granted_file(token)` → binary IPC                      | `File.arrayBuffer()`                     | `File.arrayBuffer()`  |
| Storage        | `localStorage`                                               | `chrome.storage.local` (+ change events) | `localStorage`        |
| Commands       | Native menu events and keyboard                              | Keyboard only                            | Keyboard only         |
| Clipboard      | `navigator.clipboard`                                        | `navigator.clipboard`                    | `navigator.clipboard` |

Each adapter declares `RuntimeFeatures`. Tests assert those flags agree with the capability matrix
for the matching target (`runtimeMismatches`), so the documentation cannot silently drift from the
code.

### 2.2 Document model

- **IDs:** `doc_`, `src_`, `page_`, `annot_`, `field_`, `asset_` and `op_` prefixes, plus 96 random bits, branded per type.
- **`DocumentModel`:** sources, page order, page sizes and rotation, metadata, annotations
  (markup, notes, ink, shapes, added text, added images, signatures), form fields, assets and export settings.
  Page sizes are in points with /UserUnit applied; each page keeps its `userUnit`, because
  annotation geometry is stored in unscaled PDF user space.
- **`DocumentViewState`:** current page and zoom. This is UI state, deliberately kept outside the
  model and outside undo history.
- **Operations:** `pages/rotate|reorder|insert|remove`, `metadata/update`,
  `annotations/add|replace|remove` and `batch`. Applying an operation is pure and returns its
  inverse, so undo and redo are exact.
- **History:** undo and redo stacks of `{operation, inverse}`, with a size limit and coalescing
  (e.g. dragging an annotation, typing a title). Dirty state compares the top of the history with
  a saved marker, so it stays correct across undo and redo.
- **PDF bytes:** never stored in the model or the history. Sources are referenced by ID and SHA-256;
  bytes live once in each target's resource registry.
- **Recovery snapshots:** JSON that is version-tagged, validated with zod, checked for internal
  consistency and never echoes content in its errors.

“Added text” is new content placed on a page. It is never presented as editing the PDF's
existing text objects (see [§4](#4-pdf-engines-and-licensing)).

### 2.3 Security model

**Desktop**

- The webview has no filesystem plugin. A path becomes readable only after the user picks it,
  drops it or launches Folio with it. Rust then registers it under a random 128-bit token, and
  commands accept tokens, never paths. A compromised webview (for example, a malicious PDF
  exploiting the renderer) can read only files the user already opened.
- Folio's own events and commands carry tokens and file names, never paths. Drag hover is a plain
  `true`/`false` (`folio://drag-hover`), which Rust emits from the window's drag events, so the
  UI does not listen to Tauri's `tauri://drag-*` events, which carry the paths of everything
  dragged over the window. `core:event:allow-listen` cannot be scoped by event name, so a
  compromised page could still subscribe to those built-in events and learn such paths; it still
  cannot read a file it was not granted.
- Nothing is dropped silently. Rust applies the same name rule as the workspace
  (`isLikelyPdfName`): only a name ending in `.` plus 1–8 ASCII letters or digits other than `pdf`
  counts as “not a PDF”; any other name (no extension, or one like `.v2_final`) is granted and
  checked by content. Files that are not PDFs and files that vanished before they could be granted
  come back by name and appear as a notice or an error tab.
- App commands have generated `allow-*` permissions. The `main` capability grants only those five
  commands plus `event:listen/unlisten`, `window:set-title`, `window:start-dragging` and
  `window:internal-toggle-maximize`. The tab strip is a window drag region, which the macOS
  overlay title bar relies on: drag it to move the window, double-click it to zoom or maximize.
- The CSP permits `'self'`, `ipc:`, `blob:`/`data:` images and `'wasm-unsafe-eval'` (needed for
  PDF.js image decoders), and nothing remote. The tauri-driver test asserts zero CSP violations.
- IPC errors are `{code, message}` with no paths.

**Extension**

- Permissions are `storage` and `sidePanel` only. There are no host permissions and no content
  scripts, and `externally_connectable` is not set. Tests check both the manifest and
  `chrome.permissions.getAll()`.
- The extension pages' CSP is `default-src 'self'` with `script-src 'self' 'wasm-unsafe-eval'`,
  `connect-src 'self'`, images from `'self'`, `blob:` and `data:`, fonts from `'self'` and
  `data:`, and inline styles (React style props) but no inline scripts. Pages cannot load
  remote code, and requests, beacons, images, styles and fonts to other servers are blocked
  (no CSP directive limits top-level navigation). A unit test pins the policy, and an e2e test checks
  that `fetch` and image beacons to other origins are blocked.
- The service worker validates every message with zod, caps message size and accepts only this
  extension's pages as senders. It holds no state in memory beyond a queue that orders
  activity-log writes.
- Documents never leave the device. An e2e test asserts no network requests while opening a
  document. Activity stores counts by default; file names only on opt-in, and turning that off
  erases stored names.
- Side panel → editor hand-offs are single-use IndexedDB records. Reading one deletes it, a record
  older than 10 minutes is ignored, and expired records are purged on every hand-off written or
  read, when the browser starts and when the extension is installed or updated. Folio sets no
  timer, because that would need the `alarms` permission. If the editor cannot be opened after
  the record is written, the side panel deletes the record and shows an error.

## 3. Technology decisions

| Area          | Choice                                                                             | Why                                                                                                                                              |
| ------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Desktop shell | Tauri 2                                                                            | Small installers, Rust for privileged work, a fine-grained capability system.                                                                    |
| UI            | React 19, TypeScript 6, Tailwind CSS 4, Radix primitives (shadcn-style components) | Shared across all surfaces.                                                                                                                      |
| State         | Zustand 5                                                                          | Document state (`createWorkspaceStore`) and UI state (`createUiStore`) are separate stores.                                                      |
| Rendering     | PDF.js 6, **legacy build**                                                         | The modern build calls `Map#getOrInsertComputed` and `Math.sumPrecise` natively, which macOS 13–15 WebKit lacks. The legacy build is polyfilled. |
| PDF.js assets | Bundled per target (`pdfjsAssets()` Vite plugin)                                   | CMaps, standard fonts, ICC profiles and WASM decoders load from the app's own origin. MV3 forbids remote code.                                   |
| Tests         | Vitest 5, Playwright 1.56, axe-core, `cargo test`, tauri-driver                    |                                                                                                                                                  |
| Icons         | Lucide (ISC)                                                                       | 16px at 1.75 stroke in toolbars, 14px in dense rows, 20px in empty states.                                                                       |
| Typeface      | Inter Variable (OFL), bundled                                                      | Works offline in the extension.                                                                                                                  |

### Design system

**Restrained:** neutrals tinted toward a petrol-ink hue, plus one accent used only for primary
actions, selection and focus. All tokens are OKLCH, in light and dark themes, and axe checks text
contrast in both. Pages stay white in dark mode because documents should look like documents. The
desktop UI uses a 13px base, like native apps. The extension's popup and side panel are designed
for their space rather than shrunk from the desktop layout; the extension editor page reuses the
full workspace.

## 5. Phases

Status legend: ✅ done · 🔜 next · ⏳ later.

### Phase 1: Foundation ✅

- [x] Inspect the repository and environment.
- [x] Monorepo (pnpm workspaces, root Cargo workspace), TypeScript strict mode, ESLint (+ jsx-a11y,
      react-hooks), Prettier and Vitest projects.
- [x] Shared core: document model, operations, history, recovery format; PDF engine; adapter
      contract and capability matrix.
- [x] Design system: tokens, theme, primitives, brand mark, app and extension icons (original art).
- [x] Desktop shell: token-based file grants, native menus, drag and drop, launch arguments and
      Finder events, strict capability and CSP, a file association for `.pdf`, bundle metadata.
- [x] Extension shell: popup, side panel, editor page, options, service worker, validated
      messaging, IndexedDB hand-off, activity log with privacy controls.
- [x] Shared workspace vertical slice on both targets: open (picker, drop, launch, hand-off), unlock
      password-protected files, tabs, pages list, single-page preview of the selected page,
      properties, errors, themes and shortcuts.
- [x] Real fixtures and unit, Rust, Playwright (extension and desktop UI, with axe) and native
      tauri-driver tests.
- [x] CI: checks, Linux build and native e2e on every push. macOS and Windows installers run on
      main, tags, PRs, on demand, or with `[desktop]` in a commit message.

### Phase 2: Shared PDF viewer 🔜

1. A continuous, virtualized page viewer (`editor/viewer`): render queue, canvas recycling, a
   per-zoom render cache, devicePixelRatio handling, and memory limits for 1,000+ page files.
2. Lazy page sizes: read the first page eagerly and the rest on demand, so huge documents open
   instantly. Today all page dictionaries are read up front, which is fine for typical files and
   tested at 400 pages.
3. Thumbnails in the pages panel (low-resolution renders, IntersectionObserver).
4. Zoom (fit width, fit page, custom, ⌘/Ctrl +/−, pinch) and view rotation, using
   `DocumentViewState`.
5. A PDF.js text layer for selection and copying, plus search with highlights (worker-side text
   extraction, a results panel, ⌘/Ctrl F).
6. Export the original file: desktop “Save a copy” (Rust save dialog + grant), extension download.
7. Outline/bookmarks panel.
8. Tests: a large-document performance budget (time to first page, memory), search accuracy on
   fixtures, and keyboard navigation.

### Phase 3: Core editing ⏳

- Annotation layer (pointer events, not HTML5 drag and drop, because Tauri's native drop handling
  disables DOM drag and drop on Windows): highlight, underline and strikethrough from text
  selection; notes; ink; shapes; added text; added images. Move, resize and delete, all through
  model operations and history (⌘/Ctrl Z, ⇧⌘Z / Ctrl Y).
- Page management UI: rotate, delete, duplicate, extract, reorder (thumbnail drag via pointer
  events), insert blank pages or pages from another PDF, merge and split.
- `pdf-core/export`: writes the model to a new PDF with @cantoo/pdf-lib, either as editable
  annotations or flattened. Integrity tests re-open exports with PDF.js and qpdf (`qpdf --check`).
- Metadata editing in the properties panel.

### Phase 4: Desktop integration ⏳

- Save (write back through the grant, atomically via temp file + rename) and Save As. The source
  is never overwritten without an explicit save.
- Printing: render to a print-sized PDF and hand it to the OS print dialog (plugin or native
  command per platform), with capability checks.
- Autosave and recovery: snapshots (`serializeRecoverySnapshot`) and source bytes kept in the app
  data directory and offered on restart; explicit cleanup.
- Single-instance handling (`tauri-plugin-single-instance`), so files opened while Folio runs
  arrive in the running window on Windows and Linux.
- The full keyboard-shortcut set, native clipboard, recent files and window state.
- Verify the native file dialog, drag and drop, menus and shortcuts, and Finder / Explorer file
  association on a real Mac and a real Windows PC. The capability matrix rates them Limited on
  macOS and Windows until then.
- Signed and notarized installers, once credentials exist (see README).

### Phase 5: Chrome integration ⏳

- Open the PDF in the current tab: `activeTab` plus a fetch for same-origin and public URLs, with
  optional host permissions requested at the moment of use. Clear explanations when a page or URL
  is inaccessible; authenticated URLs are retried with the user's cookies only after consent.
- Open a PDF URL and download PDF resources (`downloads` permission requested on demand).
- Save the current page as PDF via Chrome's print flow.
- Side panel tools: rotate, extract pages, convert pages to images, extract text.
- Native messaging host (`io.github.albird97.folio`): schema-validated messages with size limits,
  an allowlist of message types, a user prompt in the desktop app before any transfer, and
  graceful fallback when the app is absent. Registration instructions for both OSes.

### Phase 6: Advanced tools ⏳

Forms (AcroForm fill and flatten; XFA is reported as unsupported), signatures (drawn or image,
placement; not cryptographic signing unless a certificate flow is added), OCR (Tesseract.js, on
device), image export, compression (image recompression, object streams), password protection
(validated output), page numbers and watermarks. AI features only as optional, disclosed and
consented services.

### Phase 7: Release quality ⏳

Capability audit, accessibility review (screen readers on macOS, Windows and ChromeOS),
performance profiling, a security review (IPC fuzzing, CSP, permissions), auto-update
(`tauri-plugin-updater` with signed manifests), Web Store submission and release notes.

## 7. Known limitations

- **Viewing:** a single-page preview only; no text selection, search or zoom until Phase 2.
- **Opening:** page dictionaries are read up front. A 400-page file opens in well under a second in
  tests; files with tens of thousands of pages will be slow until Phase 2's lazy loading.
- **macOS and Windows:** the native dialog, drag and drop, menus, shortcuts and file association
  are built in CI but have not been tried on a real machine yet (Phase 4).
- **Windows:** a second file opened from Explorer while Folio runs starts a second instance (Phase 4).
- **Extension:** it cannot be the system PDF handler and cannot script Chrome's built-in PDF viewer.
  Opening PDFs from tabs or URLs arrives in Phase 5, with on-demand permissions.
- **macOS 13.3+:** required. Tailwind CSS 4 needs Safari 16.4-level WebKit.
- **Dependency pins:** ESLint 9 (end of life) is pinned until `eslint-plugin-jsx-a11y` supports
  ESLint 10.
